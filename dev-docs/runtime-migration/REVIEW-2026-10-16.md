# Runtime migration plan review — 2026-10-16

## Recommendation

**Do not approve this entire plan set for execution unchanged.** The incremental migration strategy is reasonable, and the revised plans address several important problems from the previous review. However, there are still contradictory gates, incomplete handoffs between PRs, and concrete defects in proposed replacement code. Following the instructions faithfully would not reliably produce the promised intermediate states.

This is not a recommendation to restart the design. Correct the shared contracts and dependency order first, then start the early dependency and boundary work. Hold the filesystem, process/server, harness, and runtime-switch PRs to the corrections below.

I found **11 high-priority findings (P1)** and **10 medium-priority findings (P2)**. Priority describes when the issue must be addressed, not evidence of an incident in current Quarto:

- **P1:** correct the plan before implementing or landing the affected PR; these can block the migration, corrupt file contents, break supported execution paths, or remove essential validation.
- **P2:** resolve the contract or validation gap before the affected acceptance gate; these do not block all early work.

## Scope and limits

Reviewed the README and all **45 numbered implementation plans**, together with the assessment, shared vocabulary, spikes, handoff, previous review, and supporting migration material. This was a static plan review, including focused inspection of proposed implementation and CI code. It was not an exhaustive audit of every proposed line.

The reviewed worktree was clean at the start, on `runtime-migration-plans`, HEAD `075cbf4d4`. Existing files were not changed. No tests, builds, spikes, installations, or experimental investigations were run. This review file is the only new artifact.

The findings below distinguish contradictions visible in the documents from questions needing later investigation. All proposed validation is **future work**, not a claim that a failure was reproduced. Line references identify the reviewed snapshot.

### What is already sound

- Keeping Deno as the shipping runtime during the boundary work gives the migration a useful regression baseline.
- Explicit filesystem/process/server contracts, reversible mechanical codemods, and a shrinking boundary check are the right foundation.
- The dependency lock and packaged-bundle gate, early Node CI, hidden-Deno inventory, and pre-port integration coverage address real omissions in the initial proposal.
- Keeping Julia subtree changes upstream is appropriate. Milestone J must remain an actual dependency.
- Separating the Quarto runtime from the runtime used by user scripts is necessary, as are a migration notice and a defined compatibility period.
- The plans acknowledge important compatibility issues around environment variables, certificate/proxy behavior, CommonJS interop, cache formats, and packaging.

The remaining problem is chiefly that these decisions are not consistently carried through every downstream plan.

## High-priority findings

### R01 — The standard-library boundary cannot reach the stated zero

**P1 · Correct before PR 02; reconcile PRs 22 and 25.**

**Evidence:** [PR 02](02-runtime-boundary-check.md), the `kStdModules` scanner around line 531; [PR 22](22-std-import-seams.md), lines 27–40 and its documentation addition at line 259; [PR 25](25-boundary-zero-and-monkey-patch-removal.md), lines 374–377.

PR 22 deliberately keeps direct imports of runtime-neutral std modules such as `io/*`, `async`, `crypto`, `datetime`, `streams`, and `fmt/printf`. It says the import map is their seam. PR 02 counts these same module families as boundary violations outside the runtime layer. PR 25 nevertheless requires `stdImportFiles: 0` for application and packaging code. The README also says application code must not import std directly.

An implementation can comply with PR 22 and fail PR 25. Lowering a baseline cannot resolve that policy contradiction.

**Required correction:** choose one boundary rule: either allow a documented set of runtime-neutral std dependencies, or route all of them through the runtime layer. Align the README, scanner, vocabulary, PR 22, and PR 25 with that choice. Keep hidden runtime dependencies distinct from harmless pure-library imports.

**Later validation:** a scanner fixture containing an intentionally permitted pure import, a forbidden filesystem import, and an import of a helper with an indirect Deno dependency.

### R03 — The Node bundler applies Quarto's import map inside third-party packages

**P1 · PR 26.**

**Evidence:** [PR 26](26-node-build-job.md), lines 517–540, especially the unrestricted `onResolve` callback and `resolveDir: root`; contrast [PR 31](31-test-harness-on-node.md)'s loader exclusion for `node_modules`.

The plugin processes every bare import regardless of its importer. It applies Quarto aliases and resolves the result from the repository root. A dependency's own `path` import can therefore become Quarto's std-path alias. A dependency's nested package dependency can resolve to a different root-installed version or fail to resolve at all.

This also makes the bundled execution graph differ from the unbundled test graph, whose loader deliberately leaves package-internal resolution alone.

**Required correction:** scope repository aliases to the modules they belong to. Preserve ordinary package resolution relative to the importing package, including nested versions and bare Node built-ins. Decide explicitly how mapped package entry points enter that ordinary resolution path.

**Later validation:** bundle a fixture with two versions of a transitive dependency and a dependency importing bare `path`; compare its behavior with the unbundled Node execution.

### R04 — The bundler handoff drops required CommonJS globals and an API still used by fixtures

**P1 · PRs 20b, 26, 32, and 33.**

**Evidence:** [PR 20b](20b-hidden-deno-uses.md), tree-sitter interop requirements around line 1206; [PR 26](26-node-build-job.md), lines 547 and 1549–1562; [PR 33](33-build-tooling-node.md), lines 549–592; [PR 32](32-node-ci-required.md), retention of `build-test.mjs` around line 548.

PR 20b explicitly requires `require`, `__filename`, and `__dirname` for the pinned tree-sitter UMD code. The actual banners proposed in both PR 26 and PR 33 provide only `require`. The previously identified render failure therefore remains in the proposed downstream implementation.

Separately, PR 26's public `bundle()` accepts custom `banner` and `define` options. `bundleTest()` uses those to supply test-specific `import.meta` behavior. PR 32 retains that helper for layer-script fixtures. PR 33 replaces `bundle()` with an implementation that ignores both options. Removing the CLI shim does not justify removing the fixture contract.

**Required correction:** carry the complete interop prelude into the canonical builder and preserve or explicitly migrate every remaining builder caller. Specify the CLI and fixture modes as separate supported inputs to one maintained contract.

**Later validation:** an HTML render that initializes tree-sitter, plus a retained bundled fixture that imports CLI code without accidentally executing the CLI entry point.

### R05 — Filesystem flag translation changes file contents and existence semantics

**P1 · PRs 27 and 35.**

**Evidence:** [PR 27](27-ral-fs-on-node-apis.md), `writeFlag` around line 651 and `openFlags` at lines 848–853; [PR 35](35-user-scripts-compat.md), lines 860–865 and 922–925.

The proposed `openFlags()` conflates independent options:

- `{ write: true, create: true }` selects `w`, truncating an existing file even when truncation was not requested.
- `{ write: true, truncate: true, create: false }` also selects `w`, creating a missing file.
- Append selects `a`, creating a missing file even with `create: false`.

The user-script shim has a separate content bug: `writeTextFile(..., { create: false })` uses `r+` without truncating. Replacing a longer file with shorter text leaves the old trailing bytes. PR 27 attempts to handle this case, but PR 35 does not carry that behavior over.

These can silently alter documents, generated files, and user-script output.

**Required correction:** derive flags from independent create/truncate/append requirements, using numeric open flags where necessary. Share the established behavior with the user-script shim rather than maintaining a weaker second implementation.

**Later validation:** existing/missing-file cases across create, truncate, and append; shorter replacement content; sync and async variants; both the runtime layer and the shim.

### R06 — `FsFile` gives multiple objects ownership of the same descriptor

**P1 · PR 27.**

**Evidence:** [PR 27](27-ral-fs-on-node-apis.md), `NodeFsFile`, lines 811–843.

Every access to `readable` or `writable` creates another stream around the same descriptor with `autoClose: true`. `close()` separately closes the stored numeric descriptor and never records that a stream already closed it.

Ignoring `EBADF` does not make this safe: after automatic closure, the OS can reuse that descriptor for another file. A later `file.close()` can then close the unrelated file. Repeated getter access and simultaneous readable/writable streams introduce additional competing owners.

**Required correction:** define one descriptor owner, cache stream objects, and coordinate explicit close, stream completion/cancellation, and mixed direct/stream I/O. A closed object must not operate on a recycled descriptor.

**Later validation:** stream-to-EOF followed by explicit close, cancellation followed by close, repeated getter access, and another file opened between automatic and explicit closure.

### R07 — HTTP shutdown does not cover pending binds, upgraded sockets, or disconnected response consumers

**P1 · PR 29.**

**Evidence:** [PR 29](29-ral-net-http-watch-on-node-apis.md), lines 485–513 and 519–625.

Three lifecycle gaps remain in the proposed server:

1. `shutdown()` resolves and caches its result when `server.listening` is false. If binding is still pending, the server can subsequently start listening after shutdown has supposedly completed. The supplied abort signal is only subscribed to; an already-aborted signal is not handled.
2. The forced shutdown uses `closeAllConnections()`, without ownership and termination of the server's upgraded WebSocket connections. HTTP connection cleanup is not sufficient to retire those connections.
3. Response backpressure waits only for `drain`. If the client disconnects while that wait is pending, no `close`/`error` branch settles it, and the response-body producer is not explicitly cancelled. The constructed `Request` also has no disconnect-driven abort signal.

These matter directly to preview restarts, file-serving resources, and process termination.

**Required correction:** specify bind/shutdown states and socket ownership, including WebSockets, and connect request/response cancellation to transport closure. Shutdown must settle consistently whether requested before, during, or after listening.

**Later validation:** already-aborted signal; immediate shutdown during hostname resolution/bind; active WebSocket during shutdown; and a slow streamed response whose client disconnects under backpressure.

### R08 — The advertised Deno fallback invokes Deno with Node script flags

**P1 · PRs 33 and 35, conditional on retaining the dual-runtime fallback.**

**Evidence:** [PR 33](33-build-tooling-node.md), conditional `QUARTO_RUNTIME=deno` launcher around lines 2615–2631; [PR 28](28-ral-process-on-node-apis.md), `execPath()` implementation; [PR 35](35-user-scripts-compat.md), `runOnNode()`, lines 1164–1174.

If Spike 2 passes, PR 33 keeps the option to run Quarto itself on Deno. PR 35 independently defaults user scripts to Node, but obtains that executable with `execPath()`. Under the Deno-hosted CLI, that is the Deno executable, to which the code passes Node flags such as `--require`.

The fallback can consequently fail for `quarto run` and project pre/post-render scripts precisely when users need it. Early fallback tests cannot catch a defect introduced later by PR 35.

**Required correction:** use an explicit bundled-Node locator for Node subprocesses. Define and validate the supported combinations of CLI runtime and script runtime until PR 37 retires the fallback. Audit other later Node subprocess callers for the same assumption.

**Later validation:** CLI Node/Deno crossed with script Node/Deno, including a project render hook.

### R09 — The default extension import map still exposes libraries that need an absent Deno runtime

**P1 · PR 36; related compatibility claims in PR 35.**

**Evidence:** [PR 36](36-build-ts-extension-node.md), lines 22–35, 40–41, and 990–992; [PR 27](27-ral-fs-on-node-apis.md), lines 16–18; [PR 35](35-user-scripts-compat.md), lines 25 and 1385.

PR 36 retains default std filesystem/log mappings for rebuilt engines, but loads those engines inside Quarto's Node process with no Deno shim. The plans themselves establish that `@std/fs` calls Deno internally and identify `@std/log`'s `FileHandler` as another example. Rebuilding such an engine can succeed while its filesystem or logging operation still fails at runtime.

The unchanged extension fixture only proves that a pure `path` import bundles. A warning about Deno references does not make the rebuilt engine functional. The stated remediation “authors rebuild” is incomplete for these sources.

PR 35 has a separate script shim, but its broad “stdlib imports keep working” language also conflicts with its explicit unsupported-library examples. That shim does not solve the in-process engine problem.

**Required correction:** publish a supported runtime matrix for default extension imports and script stdlib modules. Replace runtime-dependent engine mappings with compatible implementations, supply an intentional engine compatibility layer, or explicitly narrow compatibility and provide a source migration. Make the release messaging match the choice.

**Later validation:** build and load an engine that actually performs a filesystem operation and file logging, rather than only importing a pure helper. Exercise representative script stdlib operations against the shim.

### R10 — Windows integration coverage is promised downstream but skipped at its source

**P1 · Correct PR 14b before relying on it in PRs 28, 29, 32, and 34.**

**Evidence:** [PR 14b](14b-coverage-first.md), scope and acceptance at lines 38–40 and 76; [PR 28](28-ral-process-on-node-apis.md), process-group verification around line 768; [PR 34](34-installers-and-check.md), runtime-contract coverage table around line 77.

The new integration suite expects six passing checks on Linux/macOS but **one pass and five ignored tests on Windows**. The omitted checks include preview/reload and process-group behavior. Later plans nevertheless cite that suite as validating the Windows `taskkill /T` process-tree contract.

Skipping a Unix-specific pipe or signal assertion can be justified. It does not establish the corresponding Windows behavior. A green Windows matrix that ignores the relevant tests cannot support the claimed coverage.

**Required correction:** add Windows-specific behavior checks for preview lifecycle and child/grandchild cleanup before the ports rely on them. State explicitly which Unix assertions have no Windows equivalent and which need a different mechanism. Include at least one project/website preview lifecycle path, currently outside PR 14b's coverage.

**Later validation:** Windows preview reload and shutdown; termination of a started child tree; Jupyter/Julia lifecycle as applicable; argument/path cases relevant to those subprocesses.

### R11 — Deno CI retirement also removes the remaining scheduled Node coverage on macOS

**P1 · PR 37.**

**Evidence:** [PR 32](32-node-ci-required.md), lines 573–627 and Task 6; [PR 37](37-ci-switch-and-deno-removal.md), lines 189–201.

PR 32 runs the full Node suite on Linux and Windows for PRs, with full macOS Node coverage on the nightly/dispatch path. PR 37 then instructs the implementer to delete the workflow's `schedule` trigger while removing the Deno jobs. This also removes scheduled execution of `node-macos`.

The same instruction conditionally permits deleting the whole workflow if it “duplicates” `test-smokes.yml`. A reusable workflow is not itself a replacement for the trigger, bucket orchestration, and required checks that call it; PR 32 has already moved the old orchestration.

**Required correction:** specify the final Node-only workflow graph: events, OSes, bucket generation, callers, and required check names. Preserve the macOS schedule or give macOS an explicit replacement. Remove branch-protection requirements only after replacement checks exist and are observed.

**Later validation:** inspect the resulting event-to-job graph and demonstrate both a PR run and scheduled-equivalent full OS coverage. A grep proving that “Deno” disappeared is insufficient.

## Medium-priority findings

### R12 — Spike V can choose a runner that fails its own eligibility criteria

**P2 · SPIKES.md and PR 31.**

**Evidence:** [Spike V](SPIKES.md), prerequisites around line 467, selected files around lines 470–483, and decision rule at lines 555–558; [PR 31](31-test-harness-on-node.md), dependency declaration.

The spike is scheduled after PRs 02b, 23, 26, and 27b, but its required sample includes process, cache, rendering, and integration tests that depend on later process/HTTP/KV ports. Those failures can measure unfinished runtime work rather than the test runner. The decision rule then says to choose `node:test` even if neither candidate is eligible.

**Required correction:** either move the comparison after the necessary runtime ports or define a controlled common subset and classify unrelated failures explicitly. If neither runner meets the gate, record an inconclusive spike or a provisional choice; do not call it a validated outcome.

**Later validation:** rerun the eligible representative set after ports are complete before finalizing the harness and required CI.

### R13 — The harness both promises to reject and deliberately passes leaked resources

**P2 · PR 31.**

**Evidence:** [PR 31](31-test-harness-on-node.md), acceptance around line 103, sanitizer discussion, and lines 936–949.

The acceptance criteria say a leaked timer fails after a timeout. The worked example instead expects the leaking test to pass with exit code zero because the runner is forcefully terminated. Those are different guarantees. Forced exit bounds CI duration but does not establish resource cleanup, and it can conceal regressions in the exact process/server behavior being migrated.

**Required correction:** decide which resource-leak detection is retained, which is replaced by explicit lifecycle assertions, and which is intentionally lost. Keep a watchdog for hangs, but do not describe it as leak detection. Align the acceptance criteria, implementation, and documentation.

**Later validation:** separate examples for a test timeout, an unclosed child/socket, and a leaked timer, each with an intentional expected result.

### R14 — Pass-set parity can report success without complete test evidence

**P2 · PR 32.**

**Evidence:** [PR 32](32-node-ci-required.md), `readReports`/`compare`, lines 338–365, and the `always()` comparison job at line 632.

A nonexistent report path returns an empty report set. The comparison has no expected-artifact/bucket manifest or minimum result count and does not use failed sets in its `ok` calculation. Two empty inputs, or corresponding omissions on both sides, can therefore report parity. Matching failures can also disappear from the passed sets without making this comparison fail.

The underlying test jobs may still be red; this is not a claim that the whole workflow necessarily becomes green. The problem is that the parity result is not reliable evidence for the migration gate. Aggregation by name alone also loses distinct occurrences of identically named tests.

**Required correction:** validate report completeness and job status before comparing results. Use stable file-plus-test identities, account explicitly for failures, and fail on absent or malformed required evidence.

**Later validation:** missing one bucket, missing all reports on both sides, the same failed test on both sides, and duplicate test names in separate files.

### R15 — The script `Deno.Command` shim does not provide the advertised child-process contract

**P2 · PR 35.**

**Evidence:** [PR 35](35-user-scripts-compat.md), supported-member list around line 124 and `Command` implementation at lines 878–913; compare the process contract in [PR 08](08-ral-process.md) and [PR 28](28-ral-process-on-node-apis.md).

`Command.spawn()` returns Node streams directly. Deno callers using `child.stdin.getWriter()` or `child.stdout.getReader()` will fail. The code also uses one set of stdio defaults for buffered output and spawned children, and bypasses the Windows batch-command handling developed in PR 28.

This is more than a missing optional Deno member: a named supported member exposes incompatible objects.

**Required correction:** reuse the established process behavior where practical, adapting it to the Deno-shaped API. Otherwise enumerate the supported subset and reject unsupported forms clearly. Carry over stream types, method-specific defaults, and Windows command dispatch.

**Later validation:** piped Web Streams, inherited output from `spawn()`, and a Windows `.cmd` invocation through the shim.

### R16 — Any `package.json` silently suppresses the promised legacy extension configuration

**P2 · PR 36.**

**Evidence:** [PR 36](36-build-ts-extension-node.md), documented precedence at lines 32–33 and 76; `resolveConfig()` at lines 304–329.

The contract says to read `package.json`'s `quarto.build` section, otherwise fall back to `deno.json`. The implementation returns as soon as any `package.json` exists, even when it has no `quarto.build`. Adding npm dependencies to a legacy engine can therefore silently discard its entry point, output settings, and import map.

**Required correction:** base precedence on the presence of explicit Quarto build configuration, with a documented rule for mixed configurations. Make warnings describe the actual precedence.

**Later validation:** a legacy `deno.json` alongside a dependencies-only `package.json`, and alongside an explicit `quarto.build`.

### R17 — Versioned user imports are silently converted into unversioned local resolution

**P2 · PRs 35 and 36.**

**Evidence:** [PR 35](35-user-scripts-compat.md), import conversion around lines 631–645; [PR 36](36-build-ts-extension-node.md), `aliasTarget()` at lines 334–342.

Both implementations strip versions from `npm:`/`jsr:` targets and resolve whatever the local installation provides. A source request for version 1 can run version 2; two explicitly different requested versions collapse to the same resolution.

Using project npm dependencies as the new source of truth is a possible migration decision. Silently treating versioned Deno import syntax as though its version still constrains execution is not equivalent behavior.

**Required correction:** verify compatibility with the requested version, materialize the corresponding dependency, or reject version-bearing syntax with an actionable migration message. Document which lockfile governs scripts and engines after migration.

**Later validation:** requested version differs from installed version, two requested versions of one package, scoped packages, and package subpaths.

### R18 — A stale lock timeout does not prove that its writer has died

**P2 · PR 30; review the analogous build lock in PR 33.**

**Evidence:** [PR 30](30-ral-kv-on-node.md), locking decision and lines 467–507; [PR 33](33-build-tooling-node.md), stale build-lock handling around lines 703–725.

The cache lock treats age as proof of a crashed writer. A process paused by a debugger, system sleep, or slow I/O can exceed that age while still owning an in-progress read/modify/write. Another process removes its lock and enters. The first process can then resume, overwrite newer state, and remove the second process's lock in its unconditional `finally`.

The exposure is not just the narrowly described rename race or necessarily one lost cache entry. These are recomputable caches, which limits the severity, but the proposed mutual-exclusion guarantee is false.

**Required correction:** choose a locking design with ownership and a defensible stale-owner policy, or explicitly accept a weaker cache contract and design recovery around it. Do not let an old owner delete a new owner's lock. Also review corruption cleanup performed outside the write lock.

**Later validation:** pause one live writer past the stale threshold while another attempts a write, then resume it; include cancellation and crash recovery.

### R19 — Copying a directory symlink on Windows always selects a file symlink

**P2 · PR 27.**

**Evidence:** [PR 27](27-ral-fs-on-node-apis.md), `copySymlinkSync()` at lines 1490–1494 and the corresponding async path.

The code chooses the destination symlink type using `lstatSync(src).isDirectory`. For a symlink, `lstat` describes the link itself, so this does not identify a directory target. The Windows path therefore selects `"file"` even for a directory link.

**Required correction:** determine the required link type using target metadata or an explicit platform-aware link policy. Define what happens for dangling links and junctions rather than guessing from `lstat`.

**Later validation:** relative and absolute directory symlinks, a dangling link, and supported junction behavior on Windows.

### R20 — The lockfile plan overstates what an unlocked test run inherits from a warm cache

**P2 · PR 00b.**

**Evidence:** [PR 00b](00b-lockfile-and-bundle-gate.md), lines 926 and 934.

Tests retain `--no-lock` on the rationale that frozen configure populated the cache, so tests resolve locked versions anyway. Populating a cache does not constrain the full test-only dependency graph or prevent resolution of additional dependencies. The plan also permits dropping frozen enforcement on Windows if a cross-platform lock cannot be produced, weakening the stated guarantee on one supported OS.

**Required correction:** state the actual locking scope and either include test dependencies in it or track that exception explicitly. A generated aggregate entry module or supported configuration-based entrypoint list can avoid a giant Windows command line. Treat any platform-specific relaxation of frozen enforcement as a decision requiring evidence, not an automatic fallback.

**Later validation:** a cold-cache test-only dependency and a clean frozen configure on all supported OSes.

### R21 — Shared vocabulary and downstream contracts still disagree

**P2 · Correct before parallel or sequential implementation relies on the vocabulary.**

**Evidence:** [Shared vocabulary](_TEMPLATE.md), environment and exit contracts; [PR 14](14-ral-env.md), lines 96–105; [PR 27b](27b-ral-platform-env-tar-log-on-node.md), lines 29–30; [PR 28](28-ral-process-on-node-apis.md), exit/broken-pipe acceptance and implementation.

Examples:

- The vocabulary says invalid environment keys return `undefined`; PRs 14 and 27b say they throw `TypeError`.
- Exit wording describes setting `process.exitCode` and draining, while the later implementation deliberately uses synchronous writes and immediate exit.
- PR 28's early-pipe-close acceptance mentions preserving a requested status, while its proposed broken-pipe path and fixture expect exit zero.
- PR 30 replaces KV storage for both runtimes; PRs 33 and 37 still describe removing a separate Deno KV backend later.

Some of these may have straightforward intended answers. Leaving multiple authoritative answers forces implementers to invent policy and makes tests validate different contracts.

**Required correction:** settle observable behavior in the vocabulary first, then update each affected plan's code, acceptance criteria, and migration documentation. Make this a small contract reconciliation, not another architecture exercise.

**Later validation:** use one shared behavior table to drive the Deno reference and Node contract checks.

## Decisions and investigations to schedule

These are questions to answer next, not additional confirmed defects or requests to run investigations as part of this review.

1. **What exactly is the supported migration surface?** Distinguish Quarto's internal API, prebuilt engines, rebuilt engines, ordinary user scripts, scripts importing `stdlib/*`, and Deno-native scripts. For each, state supported releases, required author action, fallback, and retirement date. The current broad compatibility language hides materially different outcomes.

2. **What must remain green before the CLI flip?** The README says the complete Deno suite remains green through the boundary/migration work. PR 32 intentionally moves the full Deno matrix to nightly before PR 33, leaving a smaller per-PR sanity job. Is that reduced protection for the still-shipping runtime accepted, and what full-run result must PR 33 have before landing?

3. **What is the release rollback plan after PR 33?** The Deno fallback runs much of the same newly ported code and cannot undo a filesystem or bundler logic defect. Define when to use it, when to revert a PR, and when users must return to Quarto 1.11. Specify the prerelease soak and promotion criteria; the existence of a switch is not the whole rollback strategy.

4. **Who owns milestone J and its API agreement?** PR 36 still leaves `QuartoAPI.system.connectTcp()`/`spawnDetached()` as a discussion with PumasAI. Does Julia's upstream port need those APIs, and can that decision be made before process/network interfaces are treated as frozen? Preserve the upstream delivery dependency rather than allowing a temporary test exclusion to become the release plan.

5. **Which published support facts need fresh verification?** Runtime release pins, Node flags, package availability, Deno lifecycle claims, and minimum OS versions affect the whole design. The plans record previous checks, but this review did not repeat them. Assign a focused verification pass before relying on those facts in public messaging or installers.

6. **What constitutes packaging readiness?** PRs 33 and 34 need a shared release gate covering supported architectures and OS versions, signing/notarization, installation/upgrade/uninstall, bundled-tool discovery, and downstream consumers such as IDE integrations and package managers. Identify which external consumers parse `quarto check` output or locate the runtime. Do not release an intermediate launcher/package state between these PRs without an explicit supported configuration.

7. **What is the offline compatibility promise?** After bundled Deno removal, installing Deno alone does not necessarily provide the remote modules needed by existing scripts. Document whether offline users must preseed a cache or vendor dependencies and how a pinned, reproducible fallback is prepared before going offline.

8. **Which performance regressions are release blockers?** Parser throughput alone is insufficient. Choose a small baseline covering cold/warm CLI startup, a representative render, website discovery/copying, preview reload, and memory use. Include a meaningful Windows workload. Set thresholds before measuring to avoid accepting every regression after the fact.

9. **What is the required HTTP publishing contract?** The plans discuss cookies, redirects, proxies, and certificate trust, but the remaining assumptions about authentication endpoints and redirect behavior need an owner. Confirm the contract for redirected authenticated requests, replayable bodies, and errors under a proxy before retiring the Deno implementation.

10. **What proves the backport workflow?** Reverse codemods help with mechanical renames but do not reverse semantic changes or new error predicates. Plan one representative maintenance fix that crosses the new boundary and is backported to the supported Deno branch. Keep the manual limitations explicit.

11. **Who owns distribution compliance and maintenance?** Confirm the license/notice and provenance process for the bundled Node binary and npm dependency closure, plus who updates them during the transition and while the older Deno-based release remains supported. This is an ownership question, not a finding of a specific licensing or security problem.
