# Principal review of the runtime migration plans (2026-10-15)

Review of `00-assessment.md`, `README.md`, `_TEMPLATE.md` and plans 01–39 on
branch `runtime-migration-plans` (`main` at `b86f98d`), before any plan is
executed. Six independent reviewers (one per phase, one fact-checker with web
access) verified every plan against the code by grep and small Node 22
reproductions; the structural findings below were re-verified by hand. No
Deno binary was available, so nothing was run on Deno.

Companion to `HANDOFF.md`. Read this before executing any plan.

## 1. State of the work

- 39 plans, ~30k lines, all `planned`; no code has been executed or merged.
- The spike (Node 22, unmodified sources, 250-line shim) proved the render
  path is runtime-neutral. It did not exercise Windows, macOS, knitr, LaTeX,
  Chromium, publishing, `quarto run`, `build-ts-extension`, the test harness,
  or the build tooling. The remaining risk lives exactly there.
- The inventories in the plans are accurate (site counts, file lists,
  collision predictions). The architecture (extend `src/deno_ral/`, codemod,
  Node implementations behind the same interface, flip last) is sound.
- The plans are **not executable as sequenced**. Each phase has defects that
  would ship a regression or leave `main` red. Phase 1 is closest to ready.

| 0 (01–07) | 01 ready; 02–06 small fixes; 07 rewrite | no lockfile, bundle self-containment never checked, PR 07 would break the release bundle |

## 2. Structural findings (these change the plan's shape)

Numbered S1–S13. Everything in section 4 is a per-plan detail; these are the
ones that need a decision or a new PR.

### S1. The runtime boundary has a blind spot: JS files and std internals

The ratchet (PR 02) counts `Deno.*` in `.ts` files. These are outside it and
no plan owns them, yet PR 33 deletes the Node shim on the claim that "PR 25
made the shim unnecessary":

| Dependency | Where | When it runs | Owner today |
|---|---|---|---|
| `tree-sitter-deno.js` (`ENVIRONMENT_IS_DENO = true` at line 85, `Deno.readFileSync` at 107 and 4161) | `src/core/lib/external/` | **every render** (`render-shared.ts:44` → `initTreeSitter`), `prepare-dist`, `build-artifacts` | none (assessment 3.4 says "use `web-tree-sitter`", no PR) |
| `graphviz-wasm.js` (`Deno.env.get`, `Deno.readFileSync`) | `src/resources/js/` | runtime-loaded by `handlers/dot.ts:61`, invisible to the bundle scan | none |
| `julia-engine.js` (24 `Deno.` references, `Deno.Command`, `Deno.connect`) | `src/resources/extension-subtrees/` | runtime `import()` in `execute/engine.ts:232` | PR 36, which lands **after** PR 32 requires it; subtree is upstream-owned (PumasAI) |
| `deno-cri/chrome.js`, `external-request.js` | `src/core/cri/` | Chromium features | none |
| `core/performance/metrics.ts` monkey-patches `Deno.readTextFileSync` | `src/core/performance/` | `--profile` | PR 09 defers to PR 25, PR 25 never mentions it |
| `@std/log` `FileHandler` (`Deno.openSync`), `@std/dotenv` `load` (`Deno.readTextFileSync`, `Deno.env.set`), `readLines(Deno.stdin)` in `create/cmd.ts:259` | JSR packages | `--log`, `.env` loading, `quarto create` | PR 22 routes the specifiers, nobody reimplements them |
| `src/deno_ral/platform.ts`, `env.ts`, `tar.ts`, `log.ts` | the layer itself | always | PRs 14/19 write them on `Deno.*`; no Phase 2 plan ports them. `runtime()` always returns `deno`, so PR 31's Node branch is never taken |

**Fix:** add a "hidden dependency inventory" to PR 25's exit criteria; extend
the PR 02 ratchet to `.js` under `src/` and to the shipped resources; make PR
26's `--check-shim` scan runtime-loaded JS, not just the bundle; add two PRs
(a Phase 1 PR for tree-sitter/graphviz/deno-cri/`metrics.ts`, a Phase 2 PR for
`platform/env/tar/log/dotenv` on `node:`); start the Julia engine upstream
coordination now and move its port before PR 32.

### S2. Type-only imports break Node's type stripping (affects 31, 35, dev mode)

Node strips types but does not elide imports (`verbatimModuleSyntax`
semantics). `import { Format } from "../config/types.ts"` fails at link time
with `does not provide an export named 'Format'` (reproduced on Node 22.22).
508 files in `src/` use named imports; 62 use `import type`. Also: `<T>expr`
assertions in `src/config/types.ts`, 12 enums, 40 parameter properties, and
Node 26 removed `--experimental-transform-types`, so there is no flag to work
around enums.

PR 31 (unbundled `node --test` on sources) and PR 35 (user scripts) are
dead on arrival; PR 33's dev-mode choice (always bundle) was made for the
wrong reason but happens to avoid this.

**Fix:** one Phase 1 PR, mechanical and Deno-shippable: enable
`verbatimModuleSyntax` in `deno.jsonc`, codemod `import type` with ts-morph,
replace enums with `as const` objects, parameter properties with explicit
fields, `<T>` with `as T`. This also makes "run sources on Node with a loader
hook" a real option for the dev loop (S5 discusses why that matters).

### S3. "Node implementation, tested on Deno" under-tests the Node path

Deno's `node:http` is built on `Deno.serve`; its `fs.watch` is Deno's
watcher; PR 28's own stdin/stdout ordering deadlock passes on Deno and fails
on Node. Green Deno CI in Phase 2 proves that Deno's compat layer runs the
code, not that Node does. The only real-Node signal until PR 32 is the PR 26
job: allowed to fail, three documents, Linux, Node 22 (not 26), propped by
the shim that makes Cliffy and `@std` take their Deno branches.

**Fix:** make the Node job real from PR 26: run the `deno_ral` unit tests on
real Node per PR (bundle each test file, which sidesteps S2 until that PR
lands), and the smoke suite with a committed allowlist of known Node
failures that may only shrink (a second ratchet). Pin CI to Node 26. Bump
Deno from 2.7.14 to 2.9.x **before** Phase 2 (2.8 raised Node test-suite
conformance from ~42% to 76% and fixed `http` upgrade wiring; 2.9 targets
Node 26).

### S4. The riskiest rewrites are gated on tests that do not exist

`tests/smoke/preview/` does not exist (cited by PRs 15, 16, 17, 28, 29);
`.claude/rules/preview/overview.md` says no automated test starts the preview
server. Every Jupyter smoke test passes `--no-execute-daemon`, so the kernel
TCP transport that PR 15 rewrites has zero coverage. `tests/smoke/knitr/` and
`tests/docs/websites/book` are also cited and absent.

**Fix:** a "coverage first" PR before PR 15: preview end-to-end (serve,
WebSocket reload on file change, shutdown), a Jupyter test with
`--execute-daemon`, an `inspect | head` pipe test (see S6), a kill-grandchild
test for process groups.

- PR 33 stops downloading Deno, but `src/core/run/deno.ts:56` (`quarto run`)
  and `build-ts-extension/cmd.ts:257` still spawn it until PRs 35/36; PR 33

  workflow runs `quarto run --dev` and goes red too.
- PR 32 requires an empty Node-failure allowlist including Julia; the Julia

- PRs 15–19 add tests with raw `Deno.*` and `testing/asserts`; the ratchet

**Fix:** see section 3 (strategy). The short version: PR 33 keeps Deno as a

### S6. Runtime-environment contract regressions at the flip

None of these is in any plan except where noted:

| Behaviour | Deno today | Node | Needed |
|---|---|---|---|
| `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` for `fetch` (32 call sites: publish, `install`, extensions, `check`) | automatic | ignored unless `--use-env-proxy` (Stability 1.1, Node 24.5+) | launcher flag + test behind a proxy |
| `exit()` after large piped stdout (`quarto inspect \| jq`, `render -o -`) | sync writes, nothing lost | pipes are async on POSIX; `process.exit` truncates | layer `exit()` must drain stdout/stderr first; PR 28 maps it straight to `process.exit` |
| `QUARTO_DENO` | path to a Deno binary; conda's activate script sets it | PR 34 aliases it to `QUARTO_NODE` → runs Deno with Node flags | never alias binary paths; warn and ignore |
| `QUARTO_DENO_OPTIONS`, `_EXTRA_OPTIONS`, `_V8_OPTIONS` | Deno flags | passed verbatim to `node` → "bad option" at startup, before the warning prints | translate `--v8-flags=`, drop the rest with a warning |
| `NODE_OPTIONS`, `NODE_PATH` | n/a | PR 33 unsets them for the whole process tree: knitr, Jupyter, pre-render scripts, user `node` lose their settings | sanitise Quarto's own process only; restore for children |
| `NODE_VERSION` env override (PR 33) | n/a | collides with the variable official `node:*` Docker images set (no `v` prefix) → download 404 + reconfigure loop | rename |
| CA store (`DENO_TLS_CA_STORE=system,mozilla`) | set by launchers | `--use-system-ca` (PR 33 has it; no longer experimental in 26.12) | ok |
| Cliffy prompts `cbreak` | honoured | ignored on Node (1.3.1 source) → Ctrl-C handling differs | test |
| macOS hardened runtime | Deno entitlements | Node's own release entitlements include `disable-library-validation`; PR 34 lists two only | verify against Node's plist |

**Fix:** one "runtime environment contract" section in PR 34 that lists every
env var, flag and process-level behaviour with its Node mapping and a test.

### S7. Persistent state shared across Quarto versions

The Sass cache lives in a user-global `quartoCacheDir("sass")`, unversioned,
shared by every installed Quarto (RStudio-bundled copy and CLI). PR 18 keeps
the file name in the interface and PR 30 rewrites it as JSON with a version
bump: an older Deno-based Quarto then throws on open ("newer than supported")
or on `Deno.openKv` of a non-SQLite file. Same for
`.quarto/project-cache/deno-kv-file`. PR 30's "last writer wins per key" is
actually per file (read-modify-rename without a lock loses other processes'
writes; parallel renders and preview+render hit this).

**Fix:** backend-specific file names chosen by the backend; add cross-handle
and cross-process semantics to the KV contract test in PR 18.

### S8. Security regressions introduced by the port

- PR 28 hand-rolls `cmd.exe` quoting for `.bat`/`.cmd` (quotes only on
  whitespace, escapes `"` as `\"`): the BatBadBut class (CVE-2024-27980) that
  Deno's Rust `Command` already guards against. Use the documented
  `windowsVerbatimArguments` + full escaping, or route `.bat` through the
  existing `safeWindowsExec`, and add the injection test vectors.
- PR 19 makes a TinyTeX "writable bin dir" prerequisite a hard exit;
  `afterInstall` already falls back and warns (`tinytex.ts:408-425`). Delete
  the prerequisite.
- The `preview-shiny` control server binds `0.0.0.0` (pre-existing; PR 15
  touches the line, pass `kLocalhost`).

### S9. Dependency hygiene has no gate

- No lockfile: `deno.lock` is gitignored and every launcher passes
  `--no-lock`. PRs 03–07 add `npm:` packages with `^` ranges and Cliffy 1.3.1
  depends on `@cliffy/internal@^1.3.1`; each platform's release build resolves
  them independently.
- Bundle self-containment is never checked: `test-bundle.yml` runs `quarto
  check` only, Linux only, warm cache; lazily loaded chunks (deno_dom native
  import, puppeteer) are never executed. PR 07 as written statically imports
  `puppeteer-core` 25 + `ws` (CommonJS) into the Deno esbuild bundle without
  `platform: "node"` or a `createRequire` banner, which the spike needed.
- `deno.land` is still required after Phase 0: `package/scripts/deno_std/deno_std.ts`,
  `run_import_map.json` (`stdlib/*`), `tools/deno-esbuild-bundle.ts:7`,
  `vendor_deps.ts`, the `std@0.93.0/` redirect that four `tests/smoke/inspect`
  tests need (PR 07 deletes it).
- PR 03's "dev mode has no `--cached-only`" is false
  (`package/scripts/common/quarto:71`); every manual step after an import-map
  edit fails until re-vendoring.

**Fix:** a Phase 0 PR before 03–07: commit a lockfile and run with `--frozen`;
bundle gate = cold `DENO_DIR` + `--cached-only` + grep for external
`npm:`/`jsr:`/`https:` in `quarto.js` + real renders (HTML, website, OJS,
mermaid, manuscript) on three OSes; exit criterion `rg 'deno\.land|skypack'
src package tests tools` empty outside an allowlist.

### S10. Codemod mechanics must be fixed before PRs 10–13 run

- `getFileInfoType(fileInfo: Deno.FileInfo)` in `deno_ral/fs.ts:30` is called
  with the layer's 8-field `FileInfo` after the codemod → `deno check` fails in
  PR 10, whose instructions say "report rather than extend".
- The import merge drops aliases and `isTypeOnly` (`import { os as
  platformOs }` becomes `import { arch, os }`): concrete hits in
  `tinytex-info.ts:12` and `quarto-preview/build.ts`.
- Collision detection is not idempotent (a file that already imports
  `statSync` from the layer blocks its remaining `Deno.statSync` sites), so
  "re-run after rebase" does not work.
- PRs 08, 10–13, 14 and 22 overlap on 34–38 files and all insert imports at
  the same anchor; "independent" is optimistic.
- `realPathSync` is redefined to *not* resolve symlinks while `realPath` does;
  there are no `Deno.realPathSync(` callers in `src`, so this adds a footgun
  for nothing. Drop or rename it; map the codemod to `canonicalPathSync`.
- `@std/fs` `expandGlob`/`copy` never call `Deno.realPathSync` (only `walk`
  with `followSymlinks: true`, which no Quarto call site uses), so the
  monkey-patch removal is safe and PR 25's symlink test tests nothing.

**Fix:** PR 09 retypes `getFileInfoType`/`safeRemoveSync`, preserves
aliases/type-only imports, uses symbol-based collision checks, mirrors
`kSrcExclusions` plus `src/core/lib`; the README prescribes the landing order
08 → 22 → 10–13 → 14 and the protocol "reset the file, re-run the codemod"
for conflicts.

### S11. Backports are not considered

Stable branches (`v1.9`, soon `v1.10`) stay on Deno for a year or more. After
the codemod, every cherry-pick whose context lines include a former
`Deno.*` call conflicts. PR 37's suggestion to do the `deno_ral` rename
"right after a release branch is cut" maximises the conflict window.

**Fix:** give the codemod a `--reverse` mode (the rules are 1:1 renames) and
add a step to `checklist-backport-a-pr.md`: run the reverse codemod on the
patch before cherry-picking. Decide when Phase 1 lands relative to the
`v1.10`/`v1.11` cuts (see decisions).

### S12. CI cost is not estimated

PR 31 runs every test file in its own Node process, re-stripping and
re-resolving ~1,200 modules through a JS hook; PR 32 runs the whole suite
unbucketed on three OSes per PR (the timing file sums to ~100 serial minutes
on Linux) while the Deno matrix (20 buckets) keeps running. Expect CI minutes
to double or worse from PR 32 to PR 37.

## 3. Strategy: incremental on `main` or stacked PRs?

Two options were asked about; a third is recommended.

**A. Incremental on `main`, Deno until the switch (as planned).** Every PR
ships on Deno, the full suite gates each, reviewers verify renames by eye.
Codemods must be landed hours after being generated ("regenerate, don't
rebase": `main` had 17 `src/` commits in the last 10 days). Risk: the flip is
where atomicity matters, and the plan's PR 33 is not atomic (S5).

**B. N stacked PRs merged at once.** One review of the whole, no intermediate
prerelease exposes partial states, no backport conflicts until merge day.
Against: the stack would be a six-figure-line diff, unreviewable as a unit;
every rebase of a 1,000-site codemod conflicts; the mechanical PRs rot while
the judgement PRs are reviewed; no prerelease user tests the Node build until
everything lands; a single revert undoes months.

**C. Recommended: A for Phases 0–2, with the flip made atomic by keeping Deno
as a tool, and a dual-runtime prerelease window.**

1. Phases 0, 1, 2 land on `main` one PR at a time, in the README order
   amended by section 5. Codemod PRs are generated from fresh `main` and
   merged the same day. No stack is longer than two PRs (a layer PR and its
   first codemod).
2. The flip PR (33) switches the CLI launcher to Node but **keeps
   downloading Deno into `bin/tools`** and keeps `quarto run` /
   `build-ts-extension` on it. It is green alone. PRs 35, 36, 39 then move
   those consumers; PR 37 stops downloading Deno. "Deno always there until
   the end switch" becomes literal, and every PR in Phase 3 is independently
   revertible.
3. **Dual-runtime window (to validate with a one-week spike):** after Phase 2
   the bundle is written against `node:` APIs, so the same `quarto.js` should
   run on Deno 2.9 (`deno run` executes `node:` built-ins and
   `createRequire`). If it does, the launcher gets a `QUARTO_RUNTIME=node|deno`
   switch for one prerelease cycle: both binaries shipped, CI runs the full
   matrix on the same artifact under both, users can flip back with one env
   var. This is the strongest rollback story available and costs ~120 MB of
   installer size for one prerelease cycle. If the spike fails, fall back to
   point 2 only.
4. Backports: reverse codemod (S11). Time Phase 1 so the bulk codemods land
   right **before** a stable cut, not after, so the stable branch carries the
   new names and cherry-picks are clean for its lifetime (this is the opposite
   of PR 37's suggestion). Concretely: if 1.11 is the release that ships the
   boundary work on Deno, the codemods land before `v1.11` is cut.

Considered and rejected as the primary path: "shim-first" (flip to Node now
with the spike's shim as the runtime layer, remove `Deno.*` afterwards). It
reaches a Node binary in weeks, but ships a global `Deno` that third-party
code (Cliffy, `@std`) feature-detects, spreads semantic mismatches across
2,200 call sites instead of 10 modules, and has no definition of done. The
shim stays useful as the bridge for the Node CI job, which is what the plan
does.
